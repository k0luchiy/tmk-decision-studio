# 03. Расчётная модель (концепция)

Это **концептуальная** модель: что считаем и почему. Точная методика с формулами, коэффициентами и источниками будет в `METHOD.md` (артефакт сдачи). Здесь зафиксированы решения, которые определяют код.

## 1. Принципы модели

1. **Четыре величины разделены:** размер, трудоёмкость, срок, стоимость с риском. Не сворачиваем их в одно число раньше времени (`research/05` TL;DR).
2. **Одна декомпозиция — два сценария.** Считаем работы один раз, а затем применяем две базы затрат. Расхождение между сценариями возникает только из-за стоимости и организации, а не из-за разного объёма работ.
3. **Данные, не код.** Ставки, нормативы трудоёмкости, коэффициенты, аналоги, статьи затрат — файлы с источниками. Ядро — чистые функции без констант внутри.
4. **Диапазон, не точка.** Любой результат — распределение (P10 / P50 / P90, P80 для резерва).
5. **Три метода и их расхождение — это информация.** Если методы расходятся, показываем расхождение, а не усредняем его молча.
6. **Jev не считает.** Все числа детерминированы и воспроизводимы при одинаковых входах и версии датасета. Jev и правила только классифицируют бриф.

## 2. Единый шаблон этапов

Один шаблон для in-house и подрядчика (R5, R12). Основан на ГОСТ Р 59793-2021 (8 стадий), упрощён до 6 этапов работ и вынесен в отдельные строки приёмку и передачу знаний.

| # | Этап | Что входит | Пример работ |
|---|---|---|---|
| 1 | Анализ и требования | Обследование, сбор требований, оценка целесообразности | интервью, описание процессов, требования пользователя |
| 2 | Проектирование | Концепция, архитектура, техническое задание, оценка рисков | ТЗ, архитектурные решения, макеты |
| 3 | Разработка | Реализация функций, интеграции, рабочая документация | кодирование, интеграционные потоки |
| 4 | Тестирование | Предварительные испытания, регрессия, нагрузка | тест-кейсы, автотесты, нагрузочное |
| 5 | Ввод в действие | Пусконаладка, обучение персонала, опытная эксплуатация | миграция данных, обучение, ОПЭ |
| 6 | Приёмка и передача знаний | Приёмочные испытания, акты, передача поддержки | приёмка функционала, документация, передача |
| 7 | Сопровождение (отдельная статья TCO) | Гарантия и послегарантийная поддержка по годам | L2/L3, мониторинг, обновления |

Этап 7 не входит в срок реализации. Он идёт в TCO по годам (FR-3.5).

## 3. Размер работ: три метода

| Метод | Основа | Что даёт | Роль в итоге |
|---|---|---|---|
| **A. Bottom-up WBS** | Декомпозиция задачи на работы из архетипов (`work_archetypes.json`, 22 шт.), каждая с O/M/P | Трудоёмкость в человеко-часах по этапам и ролям | основной, вес 0,50 |
| **B. Параметрический FP-lite** | Функциональные точки (IFPUG-подобные веса), часы на FP из ISBSG-подобных PDR | Независимая проверка объёма | вес 0,20 |
| **C. Аналоговый** | ≥ 3 аналога из корпуса, приведённые коэффициентами | Оценка порядка величины по рынку | вес 0,30 |

Итоговая трудоёмкость: `E_итог = 0,5·A + 0,2·B + 0,3·C` (веса редактируемы, сумма = 1).

**Правило расхождения:** если `max(A,B,C) / min(A,B,C) − 1 > 30 %`, в вердикте выводится предупреждение «методы расходятся», и показывается, какой метод сдвигает оценку. Без предупреждения такой результат не выдаётся.

> Важно: `research/05` предупреждает, что FP ↔ SLOC ↔ story points не конвертируются универсально. Поэтому метод B работает только в FP и PDR, а не через LOC.

## 4. Трудоёмкость по работам (метод A)

Для каждой работы из архетипа:

```
E_работы = (O + 4·M + P) / 6        σ_работы = (P − O) / 6
```

Работа раскладывается по ролям по роль-миксу архетипа (сумма = 100 %), затем каждой роли назначается грейд (по умолчанию: архитектор = senior, PM = lead, остальные = middle; см. `meta.default_grade_by_role` в `work_archetypes.json`).

Сумма по работам: `E_задачи = Σ E_работ`, `σ_задачи = √Σ σ_работ²` (при независимости; при корреляции ролей ≥ 0,5 — Монте-Карло, см. §8).

**Выбор работ и объёма.** Тип работы определяется классификатором по брифу (Jev или правила). Объёмы (число интеграций, экранов, отчётов, потоков) — из брифа правилами, с подтверждением человеком. Нет объёма — берётся `typical_unit_count` из архетипа или шкала-диапазон от Jev с пониженным уровнем уверенности.

## 5. Ставки: две базы затрат

### 5.1. In-house, fully loaded (`rate_cards.json`)

```
C_FTE_мес = (ОКЛАД_gross) × (1 + взносы) × (1 + накладные)
            + офис + АРМ + ПО
C_час_внутр = C_FTE_мес / 120        (120 продуктивных часов в месяц)
```

- `ОКЛАД_gross` — из нетто-медианы роли через прогрессивный НДФЛ 2026 (не `net / 0,87`, `research/05`).
- `взносы` — 30 % до 2 979 000 ₽/год, 15,1 % сверху (точная формула, не плоские 1,30).
- `накладные` — 15 % (политика проекта, помечается как допущение с диапазоном 10–18 %).
- Офис 23 686 ₽/мес (Москва, класс B), АРМ 6 250, ПО 8 333 — все помечены источником и уровнем уверенности.

**Разовые затраты in-house** (одноразовые, в первый год):
- Найм: 1–1,5 оклада + 60 дней поиска (для технических ролей, `research/05` §6.1). Считается, если в команде нет нужного грейда.
- Ramp-up: 1–3 месяца при 25–90 % продуктивности (конфигурируется).
- Bench: при загрузке u < 100 % нужно `N_req = N / u` сотрудников (`research/05`).
- Текучесть: 10–15 % в год × стоимость замены 0,5–2 оклада (резерв в TCO).

### 5.2. Подрядчик (`contractor_rate_cards.json`)

```
C_подряд = Σ(часы_роли × ставка_роли) × (1 + приёмка_и_передача)
         + координация (10–25 % от контракта)
         + риск-премия (fixed price: 15–30 %; T&M: 0)
         ± НДС (флаг с НДС / без; ставка 20 % для РФ)
```

- Ставка подрядчика по **грейду**, не по роли (`research/07`, `contractor_rate_cards.json`): RU middle 3 700–6 600 ₽/ч, senior от 6 700 ₽/ч. Роль-множитель не применяется: это сознательное решение (`contractor_rate_cards.json` §5.5).
- Модель контракта — переключатель: T&M / fixed price / dedicated team. Меняет риск-премию и структуру оплаты.
- Для KZ, IN, PL ставки в USD, НДС не подставляется без источника (`vat_flag`).
- Гибрид: часть работ по подрядчику, часть in-house, поддержка in-house.

### 5.3. Дополнительные статьи (подключаемые, FR-2.7)

Каждая статья — отдельная строка с полями: `название`, `единица`, `количество`, `цена за единицу`, `период`, `источник`, `статус` (факт / оффер / допущение). Примеры:

| Статья | Единица | Пример источника |
|---|---|---|
| Инфраструктура (облако, стенд) | ₽/мес | допущение, КП облачного провайдера |
| Лицензии ПО | ₽/год на пользователя | `coefficients.json`, прокси 50–150 тыс. ₽ |
| Оборудование | ₽ на единицу | `research/07` §5.2 |
| GPU / LLM-токены | ₽ за 1 млн токенов или ₽/ч GPU | прайс провайдера (допущение с датой) |
| Поддержка и сопровождение | % от разработки в год | 12 % (внутр.) / 18 % (подрядчик) — `research/10` |

## 6. Сценарии и вердикт

Три сценария считаются из одной декомпозиции:

| Сценарий | Кто выполняет работы | Кто сопровождает |
|---|---|---|
| **In-house** | ДИАЙПИ / внутренняя команда, найм при нехватке грейда | ДИАЙПИ |
| **Contractor** | Подрядчик по rate card | Подрядчик (опционально) или внутренняя команда |
| **Hybrid** | Подрядчик — выбранные этапы или потоки (по умолчанию: критический путь, 2 из 6 потоков), внутри — остальное | Внутренний центр компетенций (передача по этапу 6) |

**Сценарий «пик» (R14):** сравнение найма 10 человек на время проекта (найм + ramp-up + увольнение) с подрядом на пик и передачей в поддержку.

**Вердикт** не выбирается по наибольшему числу «плюсов». Формируется правилами:

1. Если сценарии различаются по TCO-3 меньше, чем на ширину диапазона — вердикт «паритет»; решают качественные оси (передаваемость знаний, срок, ИБ).
2. Если один сценарий дешевле на старте и дороже на горизонте — вердикт условный, с точкой безубыточности (break-even, FR-3.4).
3. Гибрид рекомендуется, если выполняются оба условия: подрядчик выигрывает по сроку на критическом пути, а поддержка внутри дешевле подряда.

Текст вердикта собирается из шаблонов с подстановкой готовых чисел (свободный текст не генерируется).

**Матрица решений** (P1): 7 критериев с весами (стоимость 30, срок старта 20, передаваемость знаний 15, гибкость 10, ИБ/IP 10, управляемость 5, риск 10; Σ = 100, редактируемо). Матрица — вспомогательный инструмент, не источник вердикта.

## 7. Срок

- Длительность по критическому пути: этапы последовательны внутри потока, потоки параллельны (`research/10`).
- Команда: состав по ролям → число FTE; эффективная мощность = FTE × 120 ч/мес × коэффициент загрузки (0,65–0,75, `research/05` §5.3).
- Календарь: рабочие дни РФ (праздники из производственного календаря).
- **Сжатие срока:** если заданный срок короче базового, трудоёмкость растёт по `E ∝ t^(−4)` (закон Putnam, `research/05` §5.2). Граница разумного сжатия ~75–85 % от номинала. При сжатии > 25 % — предупреждение. Коэффициент эластичности на практике — допущение (`research/14`, КЗ-методика).
- Срок подрядчика отличается на: онбординг (2–6 недель, `research/21` §4), приёмка, координация. Срок in-house — найм (45–65 дней, если нужен новый грейд) + ramp-up.

## 8. Неопределённость

- Каждая трудоёмкость задаётся O/M/P. Логнормальное распределение по P10 и P90 для стоимости и срока (`research/05` §3.2).
- **Монте-Карло, 10 000 итераций:** сэмплируем O/M/P по работам, ставки (± диапазон), объём, с корреляцией ролей ρ = 0,5 (одно-факторная модель через гауссовский копула).
- Выход: P10 / P50 / P80 / P90 для трудоёмкости, срока и стоимости по каждому сценарию.
- **Резерв** = P80 − P50 (не «15 % на глаз»). Показываем метод.
- **Вероятностная поправка на риски:** `RE = Σ P_i × I_i` по реестру рисков добавляется как отдельная строка.
- Монте-Карло детерминирован: фиксированное зерно (seed), значение seed в отчёте.

**Совместная уверенность:** P80 по стоимости и P80 по сроку вместе не дают 80 % (`research/05` §3.2, пример 73,6 %). Это пишем в методике и в UI, если показываем обе.

## 9. Уровень уверенности (Confidence Score)

Одно число 0–100 и разложение по четырём компонентам (FR-6.1). Веса — допущение, отражено в `METHOD.md`.

| Компонент | Вес | Что измеряет |
|---|---:|---|
| Полнота брифа | 0,30 | Доля заполненных и подтверждённых параметров, обязательных для выбранного класса точности |
| Согласие методов | 0,30 | 1 − (разброс A/B/C), ограниченный 0…1 |
| Аналоги | 0,20 | Число аналогов ≥ 3 и их сопоставимость (тип, объём, регион) |
| Данные | 0,20 | Свежесть ставок, доля ставок с источником, отсутствие заглушек |

Пороги: ≥ 70 — «уверенность высокая», 40–70 — «средняя, уточните бриф», < 40 — «порядок величины, нужны данные». Класс точности (FR-1.6) ограничивает максимальный Confidence: без декомпозиции не выше 60.

## 10. Аналоги (метод C)

### 10.1. Источники

| Корпус | Объём | Что содержит | Ограничения |
|---|---:|---|---|
| `tmk_eis_rows` (ЭТП ТМК) | 60 | Предмет, НМЦК, дата, поставщик (часто), тип: 1С, SAP, SOC, поддержка, ПО | НМЦК первого лота, не победная цена (52/60 имеют победную в примечаниях); НДС не расщеплён; срок почти нигде не указан |
| `analogues` (опубликованные) | 49 | ERP, MES, CV, предиктивка, DWH, КИИ | Цена, не трудоёмкость; гранты и тоталы смешаны с контрактами; часто не в ₽ 2026 |

Аналоги разных типов **нельзя** смешивать в одну медиану (`analogue_corpus.json` §7.5). Отбор — по типу работы и масштабу.

### 10.2. Приведение

```
Цена_приведённая = Цена_аналога × K_объём × K_сложность × K_регион × K_давность × K_НДС
```

- `K_давность` — индекс по годам (инфляция). Пока CPI-ряд не подключён (`coefficients.json` → null), используется 8 %/год как **сценарный** коэффициент с пометкой «политика, не CPI». Для формального обоснования — Росстат.
- `K_регион` — по таблице `research/15` §5 (массовые роли 0,55–0,65; редкие 0,75–0,90, Москва = 1).
- `K_НДС` — приведение к виду «без НДС» (ставка 20 %, если известна).
- `K_объём` и `K_сложность` — отношения размеров по нормализованному вектору объёма (пользователи, интеграции, площадки, отчёты, объём данных, длительность, оборудование, лицензии, поддержка).

Если приводить нечем (нет вектора объёма), аналог показывается, но **не входит** в медиану; это отражается в Confidence.

### 10.3. Перекрёстная проверка

- Сравнение `C_аналоговый` и `A/B`. Расхождение > 30 % — предупреждение (FR-4.3).
- Аналоговый диапазон для демо D1 (интеграция 1С ↔ WMS) — из 1С-записей ТМК (медиана 44,5 млн ₽ на программу, разброс 30–282 млн); это разные масштабы, поэтому используется не медиана программы, а нормированная ставка (в ₽/ч через объём, если известен).

**Честное ограничение, которое говорим жюри:** до калибровки на собственных закрытых проектах аналоговый метод даёт **порядок величины**, а не точную цену. Его роль — проверка, а не замена.

## 12. Чего модель НЕ делает (и говорим об этом на защите)

- Не предсказывает точную стоимость конкретного проекта.
- Не знает внутренний прайс каталога ТМК (он не раскрыт, `research/13` §6). Заменяется прокси `rate_cards.json`, в пилоте — каталог заказчика.
- Не калибрована на закрытых проектах ТМК. MAPE и покрытие P80 — цели пилота, не результат хакатона.
- Не учитывает эффект (выгоду) проекта, только затраты. Эффект — отдельное поле в следующей версии.
- Не заменяет отчёт оценщика и обоснование НМЦК. Контур 2 (Приказ 567) выдаёт расчёт в формате обоснования, но решение остаётся за закупкой.

Для контура 2 вводим расчёт коэффициента вариации `CV = σ / среднее × 100 %` по трём и более ценам и флаг «неоднородно» при CV > 33 %.
