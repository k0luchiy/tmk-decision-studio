# Журнал решений

Требование регламента (`research/22` §8.8): решения ведутся по ходу, не в конце. Формат записи: дата, решение, альтернативы, почему, последствия, кто принял.

**Статусы:** `предложено` — ждёт решения команды; `принято` — команда согласилась; `отменено` — заменено другим решением (ссылка).

---

## D-01. Видение: инструмент поддержки решения «сделать или заказать» с диапазонами
- **Дата:** 9.11.2026 · **Статус:** предложено · **Кто:** черновик — ассистент, решение — команда
- **Решение:** продукт — «TMK Decision Studio», верхнеуровневый инструмент решения с коридором стоимости и сроков, а не точная смета (`docs/01_vision.md`).
- **Альтернативы:** точная смета по методике COCOMO; калькулятор «часы × ставка».
- **Почему:** прямое требование эксперта на Q&A (R1, `research/21` §1 п. 1, 13:26–13:31); регламент требует диапазон (`research/22` §5).
- **Последствия:** главный экран — вердикт и коридор; детальная смета вторична.

## D-02. Стек: TypeScript + React + Vite, ядро на чистом TS
- **Дата:** 9.11.2026 · **Статус:** предложено · **Кто:** команда (Q1)
- **Решение:** `shared/core` (чистый TS, Vitest), `frontend` (React + Vite), без серверной части.
- **Альтернативы:** Python (FastAPI + Streamlit); Next.js (серверная часть не нужна).
- **Почему:** оффлайн-запуск, одна среда для ядра и UI, быстрая сборка; тесты без браузера.
- **Последствия:** если команда сильнее в Python — пересмотреть до фазы 1 (`docs/05` §2).

## D-03. Только Jev, без генеративных моделей; расчёт детерминирован
- **Дата:** 9.11.2026 · **Статус:** принято (запрос команды) · **Кто:** команда
- **Решение:** Jev используется только для классификации брифа (тип работы, платформа, флаги). Генеративные модели не используются. Числа извлекаются правилами (regex + словарь), текст вердикта — шаблоны. Правила — обязательная основа, Jev — дополнение.
- **Альтернативы:** Jev + генеративная модель для чисел и текста (отклонено командой); без Jev вообще (fallback, не основной путь).
- **Почему:** требование «можно проверить и объяснить»; команда не готова добавлять полную LLM; Jev дешева и решает ровно задачу классификации.
- **Последствия:** демо работает без сети; Jev — режимы `off/cache/live` (`docs/06_jev_strategy.md` §5.3).

## D-04. Модель: `jev-1.13` в приложении, `jev-1.13-free` только для экспериментов
- **Дата:** 9.11.2026 · **Статус:** предложено · **Кто:** команда (Q8)
- **Решение:** в приложении — платная `jev-1.13` ($0,042 за 1 млн входных токенов, выход бесплатен). `jev-1.13-free` — только ручные эксперименты внутри OpenCode. Числа — правила, текст — шаблоны.
- **Альтернативы:** использовать free-модель в приложении (отклонено: free-tier предназначен для работы внутри OpenCode, ротация, лимиты по IP).
- **Почему:** документация OpenCode: «Free-tier chat models require OpenCode; use paid models from other clients»; стоимость на хакатон — центы.
- **Последствия:** нужен аккаунт OpenCode и баланс ~$5; проверка доступности из РФ в фазе 0 (Q14).

## D-06. Данные: HelpDesk — формат импорта и источник для калибровки, не для Jev
- **Дата:** 9.11.2026 · **Статус:** предложено · **Кто:** команда (Q10)
- **Решение:** выгрузку HelpDesk импортируем локально по схеме `helpdesk_import_schema.json`; в Jev не отправляем.
- **Почему:** NDA, обезличивание не гарантирует отсутствие связываемых данных; провайдеры в США и ЕС.
- **Последствия:** Jev работает только на синтетике и публичных текстах.

## D-07. Ставка по умолчанию — расчёт из `rate_cards.json`, а не константа 3 400 ₽/ч
- **Дата:** 9.11.2026 · **Статус:** предложено · **Кто:** команда (Q16)
- **Решение:** считаем fully loaded ставку по ролям и показываем среднее; 3 400 ₽/ч — как округление с источником.
- **Почему:** прозрачность происхождения числа; расхождение с `research/20` мало (~0,6 %), но пересчёт проверяем.
- **Последствия:** тест сверки с `research/10` (±2 %).

## D-08. Сценарии: in-house, contractor, hybrid на одной декомпозиции; peak — P1
- **Дата:** 9.11.2026 · **Статус:** предложено · **Кто:** команда (Q11)
- **Решение:** один шаблон этапов (6 этапов + сопровождение в TCO) для всех сценариев. Гибрид — отдельная колонка, рекомендация при выполнении правил (`docs/03` §6).
- **Почему:** R5 (идентичность этапов), R12 (приёмка в шаблоне), пожелание эксперта о гибриде.
- **Последствия:** если эксперт не подтвердит гибрид — останется как сценарий без утверждения «это мнение эксперта».

## D-09. Формат диапазона: «Мин / Средн. / Макс» на экране, P10/P50/P90 и P80 в деталях
- **Дата:** 9.11.2026 · **Статус:** предложено · **Кто:** команда (Q12)
- **Решение:** на вердикте — язык Q&A, в детализации — язык методики.
- **Почему:** R17 (эксперт) и регламент (P-диапазон) — оба должны быть видны.

## D-10. Демо: D1 как основное, D3 как гибрид, D2 — при наличии времени
- **Дата:** 9.11.2026 · **Статус:** предложено · **Кто:** команда (Q13)
- **Решение:** D1 (1С ↔ WMS, аналоги ТМК реальные) — основной сценарий; D3 (поддержка 24/7) — гибрид; D2 (CV) — резерв.
- **Почему:** D1 сильнее по данным; D3 показывает гибрид; все три в тестах.

## D-11. Калибровку не показываем как результат

## D-12. Размещение и ведение документации

## D-13. Дизайн: «родной для ТМК, лёгкая форма»
- **Дата:** 9.11.2026 · **Статус:** предложено · **Кто:** команда (Q17)
- **Решение:** визуальный язык — брендовый характер ТМК (графит, оранжевый `#EC6608`, condensed-заголовки, плоские заливки, радиус 0, без теней), но плотнее и спокойнее. Светлая тема. Полная спека — `docs/04b_design.md`.
- **Альтернативы:** «аналитическая панель» (Linear-стиль); тёмная «диспетчерская».
- **Почему:** узнаваемость для жюри + читаемость инструмента; оранжевый ≤ 2 % площади, статусы — отдельная RAG-шкала.
- **Последствия:** шрифты Barlow Condensed + Inter (OFL, локально); свой знак продукта (не логотип ТМК); перед вёрсткой — интерактивный HTML-макет.

## D-14. Jev: только классификация; числа — правила, текст — шаблоны
- **Дата:** 9.11.2026 · **Статус:** принято (запрос команды) · **Кто:** команда
- **Решение:** Jev отвечает на типизированные вопросы о брифе (`noul / choice / score`) и даёт вероятность. Числа извлекаются правилами с цитатами, формулировки — шаблоны с подстановкой чисел. Jev не считает деньги.
- **Почему:** Jev не извлекает числа и не генерирует текст — её роль ограничена классификацией.
- **Последствия:** вопросы Jev версионируются (`prompts/jev_questions.json`); конфликт Jev и правил решает человек; оценка качества на эталонном наборе из 12 брифов.

## D-15. API-адаптер и backend как источник истины
- **Дата:** 10.11.2026 · **Статус:** принято · **Кто:** команда
- **Решение:** фронт работает через HTTP API (`VITE_DATA_MODE=api`); Fastify BFF вызывает `@app/{data,core,intake,export}` и возвращает единственный набор цифр. Ответ API приводится к легаси-форме `model` адаптером `frontend/src/core/apiModel.js`; локальный `calc.js` — только fallback и режим `local`.
- **Альтернативы:** считать в браузере (`calc.js` как основной движок); полный переход UI на `@app/contract` без адаптера.
- **Почему:** два расчётных ядра давали две разные цифры; ключ Jev и Node-библиотеки PDF/XLSX нельзя держать в браузере; адаптер сохраняет готовый UI и позволяет менять расчёт без правок страниц.
- **Последствия:** `POST /api/estimates` — источник истины; при недоступности API UI честно показывает «ошибка API» и локальный демо-расчёт. История и экспорт живут на сервере.

## D-16. Jev: free-модель как fallback, ключ только в env
- **Дата:** 10.11.2026 · **Статус:** принято · **Кто:** команда
- **Решение:** приложение использует `JEV_MODEL` из окружения сервера; для демо — `jev-1.13-free`. При `402/403/404` и явно не заданной модели адаптер один раз пробует free-модель и штампует фактическую модель в ответах. `OPENCODE_API_KEY` живёт только в env backend, никогда — в репозитории или браузере.
- **Альтернативы:** жёстко зашить платную `jev-1.13`; генерировать текст/числа моделью.
- **Почему:** free-tier предназначен для работы внутри OpenCode и ротируется; без ключа демо должно оставаться рабочим. Jev по-прежнему только классифицирует, числа — правила.
- **Последствия:** `INTAKE_MODE=cache|live`, при ошибке `live` — откат на `cache`/`rules`; `GET /api/meta` показывает фактический `jevModel`. Ключ в git не попадает (проверяется `git grep`).

## D-17. Бренд продукта — «TMK Decision Studio»
- **Дата:** 10.11.2026 · **Статус:** принято · **Кто:** команда
- **Решение:** единое имя продукта во всём UI, документации и экспорте — **TMK Decision Studio** (для трека ТМК++). Историческое рабочее имя продукта выводится из актуальных документов и кода; допускается только в архиве `research/`.
- **Альтернативы:** оставить прежнее рабочее имя; использовать логотип ТМК.
- **Почему:** узнаваемость для эксперта и жюри; единое имя в заголовке вкладки, шапке, стартовом экране, страницах «Данные»/«Методика», PDF и метаданных API (`brand`).
- **Последствия:** `GET /api/meta.brand === "TMK Decision Studio"`; PDF-колонтитул и метаданные документа используют это имя; логотип ТМК как элемент бренда не используется.

## D-18. Полная матрица трёх сценариев в PDF
- **Дата:** 10.11.2026 · **Статус:** принято · **Кто:** команда
- **Решение:** PDF-отчёт рендерит не только выбранный сценарий, а полную матрицу **внутренняя команда / подрядчик / гибрид**: P10/P50/P80/P90, срок, TCO 1/3/5, стоимость P50 за час и маркер рекомендации. Матрица строится из сохранённого результата (`comparison`), а не пересчитывается в экспорте.
- **Альтернативы:** печатать один сценарий; собирать сравнение на клиенте.
- **Почему:** эксперт должен видеть обоснование выбора, а не только победителя; данные уже есть в снимке оценки.
- **Последствия:** `POST /api/estimates/:id/export` передаёт `estimates/verdict/confidence` в `buildExportBundle`; PDF содержит «Внутренняя команда», «Подрядчик», «Гибрид»; тесты проверяют это через `pdftotext`.

## D-19. Базис ставок: fully loaded остаётся основным
- **Дата:** 10.11.2026 · **Статус:** принято · **Кто:** команда
- **Решение:** in-house сценарий по-прежнему считается по `fully_loaded_hour` из `rate_cards.json` (FR-3.1). Payroll/ФОТ-базис не становится дефолтом; если он понадобится для сравнения с внешними бенчмарками, он вводится отдельным явным режимом и не меняет сохранённые оценки.
- **Почему:** требование FR-3.1 и METHOD прямо фиксируют fully loaded как базу in-house; переход на payroll сделал бы стоимость продукта несопоставимой с текущими допущениями и сломал бы провенанс ставок. Эталонные кейсы используют разные базисы, поэтому их нельзя смешивать с рабочей моделью без нормализации.
- **Последствия:** бенчмарк сравнивает текущую fully loaded модель как есть; расхождение по ставкам фиксируется в `BENCHMARK_REPORT.md`, а не маскируется сменой базиса.
