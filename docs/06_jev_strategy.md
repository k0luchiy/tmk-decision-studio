# 06. Стратегия intake: правила + Jev (без генеративных моделей)

Решение команды: в проекте используется **только Jev** (через OpenCode Zen). Генеративные языковые модели (DeepSeek, GLM и т.п.) **не используются**. Числа извлекаются правилами, текст вердикта собирается шаблонами.

## 1. Главный принцип

> **Jev не считает деньги и не выдумывает цифры.** Все числа в расчёте детерминированы, воспроизводимы и имеют источник. Jev классифицирует бриф, правила извлекают числа, человек подтверждает и то и другое.

Причина — требование кейса: «расчёт, который можно проверить и объяснить». Ответ на вопрос жюри «а что здесь от ИИ?»: **ИИ выбирает категорию и показывает уверенность; расчёт — детерминированный; человек подтверждает каждый извлечённый параметр.**

## 2. Что делает каждый слой

| Задача | Кто делает | Комментарий |
|---|---|---|
| Классификация: тип работы, платформа, флаги ИБ/КИИ, мобильность, класс сложности | **Jev** (+ правила как fallback) | Дискретные вопросы, формат Jev совпадает с задачей |
| Извлечение чисел (интеграции, экраны, срок, объём) | **Правила** (regex + словарь) | Число всегда с цитатой из текста; нет числа — пользователь заполняет |
| Формулировка текста вердикта | **Шаблоны** | Подстановка готовых чисел; никакого свободного текста |
| Расчёт трудоёмкости, стоимости, Монте-Карло | **Код** | Чистые функции, без внешних вызовов |
| Подбор аналогов, ставок, нормативов | **Данные** | Датасеты с источником |

**Вывод:** Jev используется в одном месте — классификация. Всё остальное работает без неё. Демо не зависит от Jev.

## 3. Модель Jev: что умеет и чего не умеет

Из документации OpenCode Zen (`opencode.ai/docs/console/models`, проверено 9.11.2026):

- **Jev 1.13** — модель «System One» от TypeSafe AI. Не генерирует текст: оценивает `state` (текст брифа) по **типизированным вопросам** и возвращает значения с вероятностями.
- Типы вопросов: `noul` (да/нет), `choice` (выбор из вариантов с критериями), `score` (оценка по шкале). Несколько вопросов в одном запросе обрабатываются параллельно.
- Endpoint: `https://opencode.ai/inference/systemone/v1/systemone`, заголовок `Authorization: Bearer <ключ>`. **Протокол нестандартный** (не OpenAI-совместимый) — нужен собственный адаптер.
- Модели: `jev-1.13` (платная: **$0,042 за 1 млн входных токенов, выход бесплатен**) и `jev-1.13-free` (бесплатная, ограниченное время).
- **Бесплатный уровень** по документации предназначен для работы **внутри OpenCode**; для внешних приложений официально требуется платная модель.

**Решение по модели (D-14):**
- В приложении — `jev-1.13` (платная). Стоимость на хакатон: один бриф ~2–4 тыс. токенов входных, ~10 вопросов. 300 вызовов — меньше $0,05. Минимальное пополнение консоли покрывает с запасом; бюджет в консоли — $5.
- `jev-1.13-free` — только для ручных экспериментов внутри OpenCode.
- **Доступность из РФ проверить одним запросом в фазе 0** (задача 0.6 плана). Для Jev явных ограничений по странам в документации нет, но проверка обязательна.

**Чего Jev не делает:** не извлекает числа с цитатами и не пишет текст. Поэтому она не заменяет правила — только дополняет их на уровне категорий.

## 4. Вопросы к брифу (файл `prompts/jev_questions.json`)

`state` = текст брифа. Вопросы версионируются, их порядок фиксирован.

| ID | Тип | Инструкция | Куда ложится |
|---|---|---|---|
| `work_type` | choice | «Какой тип ИТ-работы описан?» (критерии: интеграция, разработка ПО, миграция, BI/аналитика, MES/АСУ ТП, ИБ/КИИ, сопровождение/поддержка, RPA, компьютерное зрение, инфраструктура, СЭД, другое) | `Task.work_type` → архетип |
| `platform` | choice | «Какая платформа/стек?» (1С, SAP, веб (Java/React/Vue), мобильная, .NET, Python, low-code/BPMSoft, СУБД, другое) | `Task.platform` → множитель платформы |
| `security_kii` | noul | «Есть ли требования информационной безопасности, КИИ, 187-ФЗ, импортозамещения?» | флаг → статья ИБ |
| `has_integrations` | noul | «Задача включает интеграции с внешними системами?» | признак для объёма |
| `integrations_scale` | choice | «Сколько интеграционных потоков?» (0–2 / 3–5 / 6–10 / 11+) | диапазон объёма (число из правил приоритетнее) |
| `mobile` | noul | «Нужна мобильная платформа (iOS/Android)?» | коэффициент мобильности |
| `complexity` | score | «Насколько сложна задача?» (Простая / Средняя / Сложная / Очень сложная) | класс сложности → COCOMO-драйверы |
| `has_scope_numbers` | noul | «В тексте есть конкретные числа объёма (количество, срок, пользователи)?» | полнота брифа → Confidence |
| `greenfield` | noul | «Это новая система или доработка существующей?» | тип: создание / развитие |

Ответы Jev — **подсказки**, а не истина. Применяются только через таблицу проверки (§6).

## 5. Архитектура intake

```
packages/intake/
├── rules/                    # детерминированный разбор (работает всегда, офлайн)
│   ├── keywords.ts           # словарь: 1С, SAP, MES, CV, RPA, веб, мобильное, ИБ/КИИ…
│   ├── numbers.ts            # числа + единицы («6 потоков», «12 интеграций», «3 мес.»)
│   └── flags.ts              # флаги: 24/7, миграция, импортозамещение, мобильность
├── jev/
│   ├── adapter.ts            # клиент endpoint /systemone, model jev-1.13
│   ├── questions.ts          # загрузка prompts/jev_questions.json
│   └── contract.ts           # валидация ответа (zod), повтор один раз, затем rules
├── prompts/
│   └── jev_questions.json    # вопросы и критерии, версия в поле meta
├── cache/
│   └── responses.json        # кэш по хешу (вход + модель + версия вопросов)
└── merge.ts                  # объединение правил и Jev; конфликт → человек
```

### 5.1. Контракт ответа

```ts
interface JevAnswer {
  questionId: string;
  type: 'noul' | 'choice' | 'score';
  value: boolean | string | number;   // вариант или индекс шкалы
  probability: number;                // 0..1
  model: 'jev-1.13';
  promptVersion: string;
  stateHash: string;                  // хеш текста брифа
}
```

Адаптер возвращает только валидные ответы. Невалидный ответ (сломана схема, пустой value) — повтор один раз; второй провал — вопрос помечается «не отвечен», работает fallback правил.

### 5.2. Слияние (`merge.ts`)

1. Правила работают всегда и дают базовый набор параметров **с цитатами**.
2. Jev дополняет: категории (`work_type`, `platform`) и флаги, когда правила молчат или не уверены.
3. Числа (объём, срок, пользователи) — **только из правил** или рукой. Jev даёт только диапазон-шкалу (`integrations_scale`), которая используется, если числа в тексте нет, и помечается «оценка по категории».
4. Если правила и Jev расходятся по категории — в таблице проверки показываются **оба** варианта, выбор за человеком. Молча не выбираем.
5. Параметр Jev без подтверждения человека не попадает в расчёт.

### 5.3. Кэш и офлайн-демо

- Ответы Jev кэшируются по хешу (текст брифа + модель + версия вопросов) в `data/cache/`.
- Режимы: `off` (только правила), `cache` (кэш, без сети), `live` (вызовы API). Переключатель в `.env` (`INTAKE_MODE`) и бейдж в UI: «разбор: правила / Jev из кэша / Jev live».
- На защите — режим `cache`. Кэш для D1–D3 закоммичен.
- Демо работает полностью без Jev: правила дают тот же расчёт.

## 6. Таблица проверки (визуализация слияния)

| Параметр | Значение | Источник | Уверенность | Действие |
|---|---|---|---|---|
| Тип работы | Интеграция 1С ↔ WMS | правила (цитата) | высокая | ✓ |
| Платформа | 1С | Jev, p = 0,96 | высокая | принять / править |
| Интеграций | 6 | правила (цитата) | высокая | ✓ |
| ИБ/КИИ | нет | Jev, p = 0,71 | средняя | принять / править |
| Пользователей | — | не найдено | — | заполнить |

Каждая строка показывает происхождение: цитата из текста (правила) или вероятность (Jev). Пользователь видит, что именно решает машина, и может поправить всё.

## 7. Оценка качества intake

- **Эталонный набор:** D1, D2, D3 + 10–12 вариаций (короткие, длинные, без чисел, с мусором, «не ИТ-текст»). Разметка вручную до запуска.
- **Метрики:**
  - точность `work_type` (правила / Jev / итог);
  - точность флагов (ИБ/КИИ, мобильность);
  - полнота чисел: доля чисел из текста, найденных правилами;
  - доля параметров, которые пользователь в эталонном проходе **не** правил.
- **Порог:** если Jev не превосходит правила по `work_type` на эталонном наборе — Jev не включается в демо, а показывается как «экспериментальный режим». Правила остаются основой в любом случае.
- Результаты — в `TEST_REPORT.md` (раздел «Intake»).

## 8. Данные и безопасность

- В Jev отправляются **только синтетические и публичные тексты** (D1–D3, публичные ТЗ). Выгрузка HelpDesk и внутренние тексты заказчика — никогда (провайдеры в США/ЕС, независимо от политики хранения).
- Персональные данные в брифах для демо — только вымышленные (Иван Иванов / роли без ФИО).
- Ключ OpenCode — только в `.env`; в репозитории `.env.example` без значения. Перед пушем — проверка на секреты.
- Бюджет в консоли OpenCode — $5 на workspace (лимит расходов включён).

## 9. Риски

| Риск | Вероятность | Митигация |
|---|---|---|
| Jev недоступна из РФ или для аккаунта | Средняя | Проверка в фазе 0; fallback — правила |
| Протокол Jev ломает адаптер | Средняя | Контрактный тест на эталонных ответах; при ошибке — правила |
| Free-модель пропала / 429 | Высокая (если используем free) | Не используем free в приложении; кэш |
| Jev ошибается в категории | Средняя | Таблица проверки; при расхождении с правилами — человек |
| Числа не найдены правилами | Высокая | Поля заполняются вручную; шкала-диапазон от Jev как подсказка |
| Жюри спросит «зачем ИИ» | Высокая | Ответ в §10 |

## 10. Что говорим жюри

> «Jev здесь не считает стоимость. Она отвечает на простые вопросы о тексте: что это за тип работы, есть ли требования ИБ, нужна ли мобильная платформа — и показывает свою уверенность. Все числа в смете — из расчёта по формулам и источникам. Если Jev недоступна, инструмент работает на правилах и выдаёт тот же расчёт на тех же данных: это видно в интерфейсе».
