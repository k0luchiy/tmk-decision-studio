# 10 — Концепция решения: «Should-Cost / Make-or-Buy Cockpit» для ТМК++

**Составлено:** 2026-11-08. Опирается на: `01` (кейс), `03` (заказчик), `05` (методология), `06` (рынок), `07` (бенчмарки), `08` (UI-спека), `09` (хакатон и рубрика).

---

## 1. Позиционирование

**Одной фразой:** инструмент превращает свободное описание ИТ-задачи в **проверяемую и объяснимую смету** и сравнивает **две базы затрат** — собственную команду ТМК++ (АО «ДИАЙПИ») и внешнего подрядчика — на горизонте проекта и 3-5 лет, с рыночными аналогами и риск-поправкой.

**Рыночная ниша (из `06`):**
- Тяжёлые параметрические suite'ы (SEER-SEM, SLIM, PRICE, Planisware) — opaque, quoted, consultant-driven, не считают российскую специфику (30% взносов, 187-ФЗ, импортозамещение).
- Российские локальные инструменты (Project Calc, Estimate, Cash-meter, калькуляторы студий) — калькуляторы «часы × ставка», без рисков, аналогов, make-or-buy, вероятностных диапазонов.
- AI-оценщики (EstimatorGPT, UppLabs и др.) — точечные числа без калибровки, источников и аудита.
- **Пусто посередине.** Наш слоган на защите: *«COCOMO + ISBSG-логика по цене Google-калькулятора, и с рублём»*.

**Метафора из смежной отрасли:** Costimator в производстве продаёт идею **should-cost** — «знай, сколько это должно стоить, ещё до переговоров». Мы делаем **should-cost для ИТ** для промышленного заказчика, который сам является инсорсером и постоянно обязан обосновывать make-or-buy перед бизнесом.

## 2. Расчётное ядро: пять слоёв

```
 ┌──────────┐   ┌──────────┐   ┌──────────┐   ┌──────────────┐   ┌──────────┐
 │ L1 INTAKE│ → │ L2 SIZING│ → │ L3 EFFORT│ → │ L4 COST      │ → │ L5 DECIDE│
 │ текст →  │   │ FP/CFP, │   │ 3-точки +│   │ in-house vs  │   │ risk-adj │
 │ параметры│   │ WBS, SLOC│   │ PERT/MC  │   │ outsource   │   │ + break- │
 └──────────┘   └──────────┘   └──────────┘   └──────────────┘   └──────────┘
```

### L1 — Intake
Свободный текст → структурированный объект `TaskSpec`. Слой парсинга (словарь + LLM с human-in-the-loop) извлекает:
`work_type` (из таксономии ТМК++: разработка / интеграция / миграция / BI / MES / RPA / ИБ / инфраструктура / поддержка), `platform_stack` (ABAP, 1С, .NET, Java, Python, React…), `integrations_n`, `users_n`, `reports_n`, `data_volume`, `nfr` (ИБ/КИИ, 187-ФЗ, доступность), `deadline`, `existing_team`, `reusableratio`.
**Ключевое правило UX:** извлечённые параметры **никогда не применяются молча** — сначала таблица проверки (параметр, значение, уверенность, цитата из ТЗ, «подтвердить/править»).

### L2 — Sizing (три независимых метода, обязательная триангуляция)
| Метод | Основание | Формула (см. `05`) |
|---|---|---|
| **A. Bottom-up WBS** (основной) | Декомпозиция на архетипы работ | ч-ч = Σ по элементам: O/M/P трёхточечная → E=(O+4M+P)/6, σ=(P−O)/6 |
| **B. Параметрический (FP-лite)** | Объём в функциональных точках | CFP ≈ Σ(Entry+Exit+Read+Write); Effort = CFP × PDR; PDR из ISBSG-подобных бенчмарков (`07`, §7) с медианой ~6.5-10 ч/FP |
| **C. Аналоговый (Reference class)** | ≥3 рыночных аналога | Приведение: Цена_прив. = Цена_аналога × K_объём × K_сложность × K_регион × K_давность × инфляция; итог = медиана |

**Сводка:** `Effort_final = w_A·A + w_B·B + w_C·C`, по умолчанию `w = (0.50, 0.20, 0.30)`; веса редактируемы. **Если три метода расходятся >30% — это не ошибка, а фича:** расхождение показывается и требует разрешения (уточнить ТЗ / расширить диапазон).

### L3 — Effort → расписание
- Распределение по ролям из архетипных шаблонов (e.g., интеграция: аналитик 15%, прикладной разработчик 45%, системный программист 20%, QA 12%, ПМ 8%).
- Параллелизм по потокам; **критический путь**; календарь рабочих дней РФ.
- Коэффициент доступности: `продуктивные часы/мес = 120` (Klerk; из 1 320 продуктивных ч/год — `07`, §7).
- **Компрессия срока:** если asked-for T < TDEV(COCOMO II), применяется предупреждение и надбавка по закону Путнама `E ∝ t^(−4)` (см. `05`, §5): сжатие срока на 20% стоит ~ +95% трудоёмкости (граница разумного ~75-85% от номинала).

### L4 — Cost: две базы затрат (ядро make-or-buy)
**(а) In-house, fully loaded:**

```
C_FTE_мес = (S_нетто / 0.87)                     # оклад gross (Habr-данные = «на руки»)
             × (1 + τ_взносы)                     # 30% до предела 2.979 млн ₽ (2026), 15.1% выше
             × (1 + τ_накладные)                   # соцпакет, обучение, управление ≈ 10-18%
             + Аренда_рабочего_места               # ~24-56 тыс ₽/мес (NF Group / Nikoliers)
             + Амортизация_АРМ                     # ~5-7 тыс ₽/мес (Habr: 97.5k ₽ на систему)
             + Лицензии_ПО                          # прокси 5-8 тыс ₽/мес
C_час_внутр  = C_FTE_мес / 120                     # ₽/продуктивный час
```
**Пример (middle backend, 250k ₽ нетто):**gross 287.4k → ×1.30 = 373.6k → ×1.15 = 429.7k → +30k офис/АРМ/ПО → **≈ 460k ₽/мес → ≈ 3 830 ₽/продуктивный час.** Проверка по рынку: Klerk даёт in-house middle 3 100-5 600 ₽/ч — попадаем.

**Плюс in-house one-off:**
- Найм: 1-1.5 оклада + 1-2 мес. поиск (60-65 дней для ИТ) + ramp-up 1-3 мес. на 50% производительности.
- Простой (bench): если загрузка < 100%, резерв = фактическая численность × (1 / коэффициент загрузки) на время простоя.
- Текучесть: ~13% в год для разработчиков → 0.5-2 оклада на случай.

**(б) Outsource:**
```
C_подряд = (Σ_часов × ставка_rate_card × (1+наценка_приёмки_и_передачи))
           + Координация заказчика (10-25% от контракта)
           + Управление договором (≈0.3-0.5 FTE ПМО)
           + Риск-премия (fixed-price): +15-30%
           ± НДС 20% (флаг «с НДС/без», возмещаемость)
```
Ставки: RU onshore middle 2 200-6 600 ₽/ч (диапазон опросов, `07`, §6); KZ/ЦА $25-49/ч; Индия $24-41/ч; Польша/ЕС $64-76/ч. Модель контракта (T&M / fixed price / dedicated team) — переключатель, меняющий структуру риска.

### L5 — Decision
- **Вероятностная свёртка:** Monte Carlo (10 000 итераций) поверх трёхточечных оценок и корреляции между ролями (≥0.5); выход P50/P80/P90.
- **Резерв = P80 − P50**, не «15% на глаз».
- **Risk exposure:** `RE = Σ P_i × I_i` по реестру рисков (scope creep ~1%/мес; key-person подрядчика; lock-in; ИБ/187-ФЗ; текучесть инсорсинга).
- **Break-even:** `t* : Σ In-house(t) = Σ Outsource(t)` — месяц, после которого накопленные затраты собственной команды меньше.
- **TCO 3/5 лет** с поддержкой (15-20% от стоимости разработки в год), лицензиями, сопровождением.
- **NPV** при настраиваемой ставке (для приватного индустриального бизнеса в РФ/КЗ — практический диапазон 12-18%; см. `05`, §6).
- **Взвешенная матрица решений** по 6-7 критериям (стоимость 30, срок старта 20, качество/передаваемость знаний 15, гибкость/масштабируемость 10, ИБ/IP 10, управляемость 5, риск 10) — редактируется, Σ=100.

## 3. Рабочий пример (_seed-демо D1: «Интеграция 1С:ERP ↔ WMS, 6 потоков»)

| Статья | In-house (ТМК++/ДИАЙПИ) | Contractor (RU onshore) |
|---|---|---|
| Трудоёмкость (bottom-up, P50) | 930 чел.-ч | 930 чел.-ч (принята той же) |
| Ставка | 3 830 ₽/продуктивный час (fully loaded, расчёт в §2-L4) | 4 200 ₽/отчётный час (rate card) |
| Прямая стоимость | **3.56 млн ₽** | **3.91 млн ₽** |
| Найм 1С-разработчика | +0.42 млн ₽ (1.5 оклада + 60 дн. поиска) | — |
| Ramp-up (2 мес. × 50% производительности) | +0.31 млн ₽ | — |
| Координация / приёмка / передача знаний | +0.36 млн ₽ (10%) | +0.59 млн ₽ (15%) |
| **Итого реализация** | **4.65 млн ₽, 14 недель** | **4.50 млн ₽, 11 недель** |
| Поддержка 3 года (12%/год внутр. / 18%/год у подрядчика) | +1.28 млн ₽ | +2.11 млн ₽ |
| **TCO 3 года (P50)** | **5.93 млн ₽** | **6.61 млн ₽** |
| Риск-поправка до P80 | +18% (найм, текучесть, недооценка) | +9% (key-person, lock-in) |
| **TCO 3 года (P80)** | **7.00 млн ₽** | **7.20 млн ₽** |

Проверка непротиворечивости: 930 ч / (2.7 FTE × 120 ч/мес) = 2.9 мес ≈ 14 нед. (загрузка 90%); то же усилие у подрядчика на 3 FTE — 930/360 = 2.6 мес ≈ 11 нед. Break-even: подрядчик дешевле на старте на 0.15 млн ₽, но дороже в сопровождении на 0.28 млн ₽/год → **точка безубыточности инсаурсинга ≈ 6 месяцев эксплуатации (~месяц 16 от старта проекта)**.

**Вердикт инструмента:** на старте паритет (подрядчик даже на 0.15 млн ₽ дешевле), подрядчик быстрее на 3 недели; **на горизонте 3 лет инсорсинг дешевле на ~0.7 млн ₽ (10%) и оставляет знания и код внутри**; break-even — ~6 месяцев эксплуатации. Рекомендация: **гибрид** — подрядчик на срочном критическом пути (2 из 6 потоков), внутренняя команда на остальных потоках и на сопровождении.

*Что здесь важно для защиты:* расчёт **не подгоняет ответ**. Он показывает стоимость времени (3 недели × стоимость задержки вывода продукции), что и есть настоящий make-or-buy аргумент. Именно эту «стоимость времени» никто из конкурентов не считает.

## 4. MVP на 36 часов (stop-code 10.11 22:00)

**P0 — обязательно (демо рушится без этого):**
1. Экран-кокпит: левый рельс «Бриф» + центр «Ответ» + правый рельс «Сравнение» (спека в `08`, §7).
2. Intake: textarea → извлечение параметров → **таблица проверки** с цитатой и уверенностью → подтверждение.
3. Ядро: bottom-up WBS с трёхточками (A) + FP-lite параметрика (B) + ≥3 аналога (C) — все три показываются.
4. Два сценария затрат с полной разбивкой по статьям; добавление НДС-флага, взносов 30%/15.1%.
5. P50/P80 через Monte Carlo (однолинейная реализация 10 тыс. итераций — миллисекунды).
6. Графики: **break-even**, **tornado (чувствительность)**, стек TCO 3 года. Каждый — с кнопкой «таблица».
7. **Формула-древо** по клику на любое число (как «Data Source» в TurboTax).
8. Экспорт **PDF** (1 страница решения + приложения) — обязателен, это «полный сценарий».
9. Seed: три демо-задачи D1-D3 (`01`, §7).

**P1 — сильно улучшает:**
10. Матрица решений с редактируемыми весами; NPV; сценарные вкладки и diff; реестр рисков с P×I; режим Target (обратный solve); XLSX-экспорт; «поделиться» ссылкой-снимком.

**P2 — если останется время:** калибровка на 3-5 исторических проектах (показать MAPE), командный планировщик по календарю, импорт ТЗ из файла, тёмная/светлая темы.

**Минимальный стек:** Next.js + TypeScript + Tailwind/shadcn + Recharts + SQLite (или чистый клиентский стор) + `fast-json-patch` для diff; ядро расчёта — отдельный pure-TS модуль с unit-тестами (`expect(calc(...)).toMatchSnapshot()`), задающий defaults из `07`.
**Демонстрация устойчивости:** ядро покрыто тестами на 3 seed-кейса — это аргумент на критерии «техническая реализация» и «обоснованность».

## 5. План защиты (5-8 минут, ~90 секунд демо)

| Время | Что делаем | Закрываемый критерий |
|---|---|---|
| 0:00-0:20 | Проблема: «заказчик сегодня решает это на глаз; existing tools are opaque or trivial» (1 слайд, 3 иконки из `06`) | Понимание кейса |
| 0:20-1:50 | **Живая демка на D2 (CV-чекер)** — вставляем ТЗ, подтверждаем извлечённые параметры, меняем одно допущение на глазах жюри (ставка подрядчика), пересчёт, показываем break-even и tornado | Работающий прототип, полнота сценария, UX |
| 1:50-2:40 | Открываем формулу-древо: «вот why 4.2 млн: 930 ч × 4 200 ₽ + 15% координации; вот источник ставки и дата» | Объяснимость/проверяемость (буквально из текста кейса) |
| 2:40-3:20 | Аналоги: 3 контракта из открытых данных + приведение коэффициентов; сравнение с параметрической оценкой; предупреждение о расхождении | Рыночные аналоги (bullet 3 кейса) |
| 3:20-4:00 | Риски и допущения: чипы, реестр, P80-резерв | Риски и допущения (bullet 3) |
| 4:00-4:30 | PDF-выгрузка на экран; «это документ, который можно приложить к договору/бюджету» | Реализуемость, ценность для ТМК |
| 4:30-5:00 | Границы: «мы не предсказываем будущее, мы делаем ошибку измеримой; калибровка на истории — план пилота» | Честность → доверие жюри |

**Ожидаемые вопросы жюри и ответы (заранее):**
- *«Чем это отличается от Excel?»* → версионирование сценариев, вероятностные диапазоны, аналоги с приведением, формула-дерево, экспорт; Excel не хранит provenance.
- *«Откуда ставки?»* → каждый источник с датой; всё редактируемо; подключается внутренний каталог услуг/себестоимость ТМК++ (у заказчика уже есть «прозрачная себестоимость и цена» на услугу — см. `03`).
- *«А если врать в допущениях?»* → divergence-алерт между 3 методами + tornado показывает, какие допущения определяют итог; чувствительность к манипуляции — это фича.
- *«При чём здесь ИИ?»* → extraction + Explainability, human-in-the-loop; никаких некалиброванных «предсказаний».

## 6. План пилота для ТМК++ (слайд «что дальше»)

1. **Неделя 1-2:** загрузка внутреннего каталога услуг ТМК++ и фактической себестоимости (заказчик её уже считает — `03`), rate card подрядчиков из закупок.
2. **Неделя 3-4:** ретроспективная калибровка на 10-15 закрытых проектах (у Проектного офиса ТМК ~150 проектных активностей в год, 40% с ИТ-составляющей — `03`): цель MAPE ≤ 30% и покрытие P80 ≥ 80%.
3. **Квартал 2:** интеграция с ЭТП закупок ТМК (zakupki.tmk-group.com) для автоматического подбора аналогов из договорной базы — **это и есть data moat:** закрытые данные о реальных ценах российских ИТ-контрактов недоступны конкурентам.
4. **Метрика ценности:** доля ИТ-инициатив с рассчитанным make-or-business перед стартом; среднее отклонение факта от P80.

## 7. Отказ от универсальности (важно для доверия)

Мы не претендуем на точность предсказания. Мы поставляем:
1. **Явную структуру затрат**, которой раньше не было.
2. **Диапазоны с заявленной вероятностью** вместо точек.
3. **Провенанс каждой цифры.**
4. **Чувствительность** вместо уверенности.

Это ровно то, что требует кейс: *«расчёт, который можно проверить и объяснить»*.
